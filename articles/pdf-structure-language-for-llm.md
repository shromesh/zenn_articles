# はじめに

こんにちは、[株式会社Prefab](https://corp.prefabdeli.com/) CTOの[米本](https://x.com/shromesh_app)です。

[前回の記事](https://zenn.dev/prefab/articles/072d7768bd769c)では、私たちがなぜ建設×積算という課題に取り組んでいるのかについて書きました。今回は、その課題を技術的にどう解くのかという話をします。

# まず、積算業務で何が行われているのか

積算業務の具体的な手順を知らないと、この先の話がピンと来ないと思います。実際の電気図面を見てみましょう。

![電気設備の施工図面](/images/pdf-structure-language-for-llm/chichibu.jpg)

これは、ある建物の電気設備図面です。積算担当者はこの図面を見て、以下のような作業を行います。

1. **シンボルの認識と数え上げ**: 図面上に散らばっている丸や四角の記号が、コンセント、スイッチ、照明器具、感知器などの電気設備を表しています。これを1つ残らず見つけ、種類ごとに数えます。
2. **配線の追跡**: シンボル同士をつなぐ線が配線です。線種やスラッシュ、傍記によって意味が異なります。どのブレーカーからどの機器まで、どんな線種で繋がっているかを追跡し、回路構成を把握します。
3. **拾い出し**: 認識したシンボルの数量と配線の長さから、必要な部材（ケーブル、コンセント、スイッチ、配管など）の数量を算出します。
4. **図面の間違いを見つける**: 設計図面にはミスが含まれていることがあります。たとえば、壁がないのに床配線から天井配線にいきなり切り替わっており、どこで床から天井に持ち上げるのか考慮されていないケースや、線が短すぎて一点鎖線なのに実線に見えてしまうケースなど。こうした矛盾を積算担当者が発見し、設計者に確認を取る作業も発生します。

この作業を、人間が目視で1枚1枚行っています。1つの案件で数十枚の図面があり、1ヶ月以上かかることも珍しくありません。

# LLMにこの作業を任せられないか？

LLMは非常に賢いです。ならば、この図面を渡して「シンボルを数えて、配線を追跡してくれ」と頼めば済む話ではないでしょうか。

結論から言うと、現状のLLMでは無理です。2つのアプローチを試しましたが、どちらも積算に使える精度には達しませんでした。

## アプローチ1: 図面画像をVision LLMに渡す

Claude Opus 4.6やGPT-5、Gemini 3 Proなどに図面画像を渡すと、「分電盤がある」「配線が引かれている」程度の大まかな認識はできます。

しかし、積算業務が求める精度には到底届きません。

- コンセントの個数を正確に数えられない（15個を「約12〜18個」と回答するレベル）
- 線種（実線・破線・一点鎖線）の区別が曖昧
- 配線の接続関係（どの機器からどの機器へ繋がっているか）を追跡できない
- 図面記号の微妙な違い（接地コンセントとアースターミナルなど）を混同する

LLMの画像認識能力は自然画像（写真、イラストなど）で訓練されています。建設図面のような非自然画像、つまり密集した記号、交差する線、微妙な線種の違いが含まれる画像に対しては精度が大きく落ちます。

積算とは、すべての部材を1つ残らず数え上げる作業です。「だいたいこれくらい」では使い物になりません。

## アプローチ2: PDFのベクター命令をそのまま渡す

PDFはただの画像ではありません。内部に「描画命令」を持つベクターデータです（詳細は後述します）。この描画命令をテキストとしてLLMに渡せば、画像認識よりも正確に解析できるのではないでしょうか。

実際の電気図面のPDFから抽出した描画命令は、こんな内容が数千行にわたって続きます。

```
q
0.24 0 0 0.24 0 0 cm
q
1 0 0 1 0 0 cm
/GS0 gs
q
1 0 0 1 0 0 cm
0 0 2480 3508 re
W n
q
3.125 0 0 3.125 0 0 cm
...（数十万行続く）...
```

テキスト情報が豊富に埋め込まれたPDFであれば、LLMはかなり賢く応答します。「この部屋にこのシンボルが何個あります」といった質問にも答えてくれることがあります。しかし、そんな優しい図面ばかりではありません。テキスト情報が乏しく、パス情報（線や図形の描画命令）を解読しなければシンボルや配線を識別できない図面が体感で7割ほどあります。そうした図面でも、LLMがいい感じにパスを解釈して「丸が何個ある」程度の回答を返してくれることはあります。これ自体はすごいことです。しかし、数十万行の描画命令を処理するには時間がかかりすぎる上、座標変換行列の入れ子を正確に追跡したり、複雑なシンボルと配線の接続関係を復元したりするには精度が足りず、実用レベルには達しません。

つまり、**画像として渡しても、生データとして渡しても、LLM単体では図面を理解できません**。これが出発点です。

# 類推: PowerPointとpptxgenjs

ここで1つの類推を紹介します。

PowerPointファイル（`.pptx`）もPDFと同じく、人間が直接読み書きできないバイナリ形式です。LLMが`.pptx`の中身を直接解釈するのは不可能に近いです。

Anthropicの公式リポジトリ [anthropics/skills](https://github.com/anthropics/skills/tree/main/skills/pptx) では、この問題を[pptxgenjs](https://github.com/gitbrent/PptxGenJS)というライブラリで解決しています。`.pptx`というバイナリを直接扱うのではなく、JavaScriptのコードとしてスライドの内容を表現することで、LLMが理解・生成できる形にしています。

```javascript
const pptxgen = require("pptxgenjs");
let pres = new pptxgen();
let slide = pres.addSlide();
slide.addText("Hello World", {
  x: 1, y: 1, w: 8, h: 1,
  fontSize: 36, bold: true, color: "363636"
});
pres.writeFile({ fileName: "output.pptx" });
```

解釈不能なバイナリ → 解釈可能な言語（JavaScript）への変換。これによって、LLMがPowerPointを自在に扱えるようになっています。

**私たちがPDFに対してやろうとしていることも、本質的にはこれと同じです。** PDFの解釈不能な描画命令を、LLMが理解できる構造化データに変換します。ただし、PowerPointとは比較にならないほど難しいです。PowerPointはスライドの構造がある程度決まっていますが、PDFの図面では数十万行の描画命令から「図形としての意味」を復元しなければなりません。難易度が跳ね上がります。

# PDFの内部構造

では、PDFの描画命令とは具体的にどんなものでしょうか。ここからが技術的な本題です。

## PDFは「描画命令の列」である

PDFファイルを開くと、人間の目には図面や文書が見えます。しかしPDFの中身は、「この座標に線を引け」「この領域を塗りつぶせ」といった低レベルな描画命令の羅列です。

各ページには**コンテンツストリーム**と呼ばれるバイト列が格納されており、その中にオペレータ（命令）とオペランド（引数）が並んでいます。たとえば、ある電気図面のPDFから抽出したコンテンツストリームの一部は、こんな形をしています。

```
q
1 0 0 1 150.5 420.3 cm
0.0 0.0 0.0 rg
0.5 w
200 300 m
350 300 l
350 450 l
200 450 l
h
S
Q
```

これは人間にとってほぼ意味不明ですが、PDFビューアはこれを正確に描画できます。各命令の意味を解説すると以下のようになります。

| 命令 | 意味 |
|------|------|
| `q` / `Q` | グラフィックス状態の保存・復元（スタック操作） |
| `cm` | 座標変換行列（CTM）の適用。6つの数値でアフィン変換を定義する |
| `rg` | 塗りつぶし色をRGBで指定（0.0 0.0 0.0 = 黒） |
| `w` | 線の太さを指定（0.5ポイント） |
| `m` | 指定座標へ移動（パスの始点） |
| `l` | 現在位置から指定座標まで直線を引く |
| `h` | パスを閉じる（始点へ線を引く） |
| `S` | パスをストローク（輪郭線を描画）する |

つまり上記のコンテンツストリームは、「座標(200,300)を起点とする長方形を黒い線幅0.5の線で描画せよ」という意味です。

## 座標変換行列（CTM）という罠

PDFの座標系は、原点がページ左下にあり、1単位 = 1/72インチです。ここに`cm`オペレータによるアフィン変換が重なります。

```
a b c d e f cm
```

この6つの数値は、以下のような変換行列を表しています。

```
| a  b  0 |
| c  d  0 |
| e  f  1 |
```

`cm`は入れ子にできます。`q`で保存した状態に対して`cm`を適用し、描画後に`Q`で戻す、というパターンが頻出します。あるパスの実際の座標を知るには、スタック上の全ての変換行列を順に乗算しなければなりません。

たとえば、以下のような入れ子構造を考えます。

```
q
  1 0 0 1 100 200 cm    % 平行移動(100, 200)
  q
    2 0 0 2 0 0 cm      % 2倍拡大
    50 50 m
    100 50 l
    S
  Q
Q
```

この場合、`50 50 m`の実際の座標は (50×2+100, 50×2+200) = (200, 300) です。単純に数値を読み取るだけでは正しい位置がわかりません。

## 同じ見た目、異なる表現

PDFの厄介さは、同じ見た目を複数の方法で表現できる点にあります。

たとえば、幅2ポイントの水平線は以下の2通りで表現できます。

**方法1: ストロークとして描く**
```
2 w
100 300 m
500 300 l
S
```

**方法2: 塗りつぶし矩形として描く**
```
100 299 400 2 re
f
```

方法1は「太さ2の線を(100,300)から(500,300)まで引け」という命令です。方法2は「(100,299)に幅400、高さ2の矩形を塗りつぶせ」という命令で、結果は視覚的にほぼ同じになります。

同じ視覚的要素が異なるオペレータの組み合わせで表現されるため、「この線は同じ配線を表している」と判断するには、描画結果のレベルでの解析が必要です。

## 破線もまた厄介

電気図面では実線と破線で意味が異なります。接地線、隠れ配線、補助線など、線種が情報を持っています。

厄介なのは、PDFにおける破線の表現方法が1つではないことです。

**パターン1: 途切れ途切れのパス情報**。短い線分が何本もバラバラに配置されているだけで、「これは1本の破線である」という情報はどこにもありません。人間は視覚的に「これらは1つの点線だ」と解釈しますが、その認知をアルゴリズムで再現する必要があります。

**パターン2: dashes属性による表現**。1本の連続した線に対して、破線パターンが属性として付与されているケースです。

```
[3 2] 0 d     % 3ポイント描画、2ポイント空白、位相0
100 300 m
500 300 l
S
```

この場合は属性を読み取ればよいので比較的扱いやすいですが、すべての図面がこの方式とは限りません。

**パターン3: 白線の上書き**。黒い実線を1本引いた後、コンテンツストリーム上のまったく別の場所で、その上から白い線を等間隔に塗り重ねることで、結果的に破線に見せている図面もあります。描画命令を上から順に読んでも、黒線と白線が離れた場所に記述されているため、両者の関係に気づくこと自体が困難です。

このように、同じ「破線」でもPDF内部での表現方法がバラバラです。これをLLMに直接解釈させるのは筋が悪く、事前にアルゴリズムで正規化する必要があります。

# 画像認識とアルゴリズムで「構造」を復元する

PDFの内部がこのような状態である以上、LLMに渡す前に、私たちが図面の構造を復元する必要があります。

画像認識、グラフアルゴリズム、幾何学的解析。使えるものはすべて使い、図面の意味構造を組み立てていきます。ベクターデータとして得られる幾何学的情報と、画像として得られる視覚的情報の両方を活用しながら、図面特有の性質やドメイン知識も泥臭く組み込んでいく作業です。

最終的な出力は、たとえば以下のようなJSONです。

````json
{
  "symbols": [
    {
      "type": "コンセント2P20A",
      "position": [1400, 1000],
      "connected_to": ["circuit_1"]
    },
    {
      "type": "ブレーカー20A",
      "position": [800, 500],
      "connected_to": ["circuit_1", "circuit_2"]
    }
  ],
  "circuits": [
    {
      "id": "circuit_1",
      "from": "ブレーカー20A",
      "to": ["コンセント2P20A", "照明_A"],
      "line_type": "実線",
      "wire_spec": "VVF2.0-2C"
    }
  ]
}
````

ブレーカーからどの照明まで1つの回路で繋がっているか、どの線種でシンボル同士が結ばれているか。この構造データがあれば、LLMは図面の内容について高精度な推論を行えます。


# この先に見えているもの

私たちが目指しているのは、シンボルや配線を数える積算業務の自動化だけではありません。PDF図面上のあらゆる知的作業をLLMに任せられる世界を作ろうとしています。

構造言語化されたデータをLLMに渡せるようになると、何が起きるでしょうか。具体的に4つの未来が見えています。

## PDF図面からCADを再作成する

建設業界には、過去数十年分のPDF図面が眠っています。紙の図面をスキャンしたもの、古いCADソフトから出力されたもの。設計データは失われていても、PDFだけは残っています。

改修工事のたびに、設計者はこのPDFを横に並べ、目視で読み取りながらCAD上に一から図面を引き直しています。シンボルの位置、配線ルート、線種、テキスト注記、すべてを手作業で再現します。この作業に何日もかかります。

構造言語化が完成すれば、この再作成作業をLLMに任せられます。PDFから抽出された回路構造とシンボル配置をそのままCADフォーマットに変換します。人間がPDFとCADを見比べながら行っていた作業が、自動化されます。

## PDF図面から設計ノウハウを学習する

熟練した電気設計者は、数百枚の図面を描いてきた経験から「この用途の建物なら、この回路構成が最適だ」といった暗黙知を持っています。この知識は属人的で、引き継ぎも難しいです。

構造言語化された図面データは、この暗黙知をLLMに学習させる教師データになります。病院の図面には非常用回路がどう設計されているか、商業施設ではどの程度のコンセント密度が標準か。数千枚の図面から抽出された回路構造のパターンを、LLMは言語として読み取り、設計上の判断基準を獲得できます。

## コストダウン案をAIが提案する

「この配線ルートを変えれば、ケーブル長を15%短縮できます」「この照明回路は分岐を統合して、ブレーカーを1台減らせます」。回路構造がグラフとして表現されていれば、こうした最適化提案は経路探索の問題になります。

構造データを持ったLLMは、回路構成を俯瞰して無駄を指摘できます。人間の設計者が見落としがちな、図面全体を横断したコスト削減の余地を発見します。設計レビューの品質が根本的に変わります。

## 回路の書き間違いをAIが自動修正する

接地線の接続漏れ、定格を超えた回路への機器接続、凡例と図面記号の不一致。こうした書き間違いの検出は、現在は熟練者の目視チェックに依存しています。

回路構造がJSON/YAMLとして表現されていれば、LLMは電気設備の知識と照合して矛盾を検出できます。「このブレーカーの定格は20Aだが、接続されている負荷の合計は25Aを超えている」「この系統に接地線が接続されていない」といった指摘を自動で生成します。チェック作業の時間と見落としの両方を削減できます。

## 私たちが作っている「前処理」の意味

これら全ての未来に共通する前提は、PDFの描画命令が構造データに変換されていることです。LLM単体では、PDFの生データも図面画像も正確には理解できません。

私たちがやっているのは、画像認識、グラフアルゴリズム、幾何学的解析、そして図面ドメインの知識をフル活用して、LLMにはできない部分をカバーする前処理基盤を作ることです。LLMが建設図面上のあらゆる知的作業を代替する時代。その実現に必要な「PDFとLLMの間の翻訳レイヤー」を構築しています。

# おわりに

PDFは一見ただのドキュメントフォーマットに見えますが、その内部は描画命令の羅列であり、意味的な構造を持っていません。この構造のなさが、PDF図面をAIで処理する際の根本的なボトルネックです。

私たちは、画像認識やアルゴリズムを駆使してこの壁を突破し、LLMが図面を自在に扱える未来を作ろうとしています。積算の自動化はその第一歩にすぎません。

この挑戦に興味を持ってくださった方は、ぜひ[前回の記事](https://zenn.dev/prefab/articles/072d7768bd769c)もあわせてご覧ください。
